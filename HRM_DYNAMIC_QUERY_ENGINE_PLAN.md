# HRM Dynamic Query Engine plan

## Objective and current architecture

Chat Backend authenticates the user and sends its user ID and request ID to HrmMCPServer. HrmMCPServer forwards them with an internal token to `hrm-server`. `AuthorizationRepository.resolveActor` resolves the single `hrm_identity_links` row, active employee, company, department, roles, and permissions. HRM PostgreSQL access belongs to `hrm-server` only. There is no client-selected company or employee identity. Missing links fail closed.

Existing MCP read tools are employee list/search/profile, department list/details/overview/members, attendance and leave lists, project/task lists, and legacy self/team business reads. Mutation tools create leave requests and tasks, assign tasks, and update status. The self/team attendance summaries, leave balance/preview, approval, and task transitions contain business rules and remain separate. Existing tools and endpoints remain for compatibility; no catalog removal is justified until equivalent authorization and agent behavior are verified.

Schema reviewed: migrations 001–006 define companies, departments, positions, employees, identity/RBAC, attendance_records, leave_requests, projects and tasks with company-scoped foreign keys. Employee-to-department and attendance/leave-to-employee joins must include company ID. No salary table or salary field exists. Identity/RBAC, audit, leave approvals, and credentials are outside the DQE registry. Employee email is treated as a restricted field; self/team readers do not gain company-wide employee aggregation.

## Design and decisions

Use `POST /internal/v1/query` with the existing internal authentication and a single `query_hrm_data` MCP tool. Query JSON may name only registered datasets and fields. The backend owns SQL identifiers, joins, row scope, permissions, limits and timeout. Values use PostgreSQL parameters. All list and aggregate queries include company scope. The registry initially covers employees, attendance records and leave requests; employee department name is a fixed, company-matched join. Scope is selected from existing permissions, with the narrowest applicable scope for self/team datasets unless a broader existing permission explicitly permits it. Employee dataset requires `employee.profile.read.any`. No new database tables or permissions are needed.

Supported query shape: `dataset`, optional `select`, `filters`, `sort`, `aggregations`, `groupBy`, `limit`, `offset`. Query validation rejects unknown keys, unsupported combinations, invalid types/operators, arbitrary SQL/JOIN, oversized requests and unapproved fields. Aggregate aliases have bounded identifiers. Result envelope contains rows, dataset, count, limit and offset. Grouped aggregates with small groups may permit inference, so only fields already available at the actor's row scope may be aggregated; no sensitive numeric fields are registered.

Registered datasets and scope:

| Dataset | Allowed fields | Scope |
|---|---|---|
| `employees` | id, display_name, department_id, department_name, title, employment_status; email is select/filter only | `employee.profile.read.any` plus company |
| `attendance_records` | id, employee_id, work_date, status, minutes_worked | `attendance.read.team` in linked department, otherwise `attendance.read.self`; company; required work_date range <= 366 days |
| `leave_requests` | id, employee_id, leave_type_id, start_date, end_date, requested_days, status | `leave.read.self` plus linked employee and company |

Available operators: eq, ne, gt, gte, lt, lte, in, between, contains. Contains is only for text and escapes SQL wildcards. The numeric functions sum/avg/min/max need a numeric field; count accepts any allowed aggregate field or all rows. Limit is 1–100, offset 0–10000, filters <= 8, sort keys <= 3, group keys <= 2, aggregations <= 5. SQL runs in a read-only transaction with a 3 second statement timeout. The HTTP body limit is 64 KiB. PostgreSQL errors are returned as `HRM_INTERNAL`, without raw SQL or driver details.

Example contract for “Which department has the most active employees?” (requires `employee.profile.read.any`):

```json
{"dataset":"employees","filters":[{"field":"employment_status","operator":"eq","value":"active"}],"groupBy":["department_name"],"aggregations":[{"function":"count","alias":"total"}],"sort":[{"field":"total","direction":"desc"}],"limit":20}
```

The generated SQL uses the fixed company-matched department join, adds `e.company_id = $1 AND e.employment_status = $2`, groups by `d.name`, orders by `total`, and limits the result. `department_name` may be null for employees without a department; callers should label that group accordingly.

## Worked execution trace and before/after

Before: Agent selected one of the fixed MCP read tools, which called a fixed HRM API endpoint and repository query. A grouped active employee count had no direct read capability. After: Agent constructs the JSON above and calls `query_hrm_data` in `HrmTools.cs`; `HrmApiClient.QueryDataAsync` forwards it with `X-Actor-User-Id`, request ID and internal token; `app.js` validates those headers in `internalContext` and calls `HrmService.resolveExecutionContext`; `AuthorizationRepository.resolveActor` reads the linked active employee and RBAC permissions; `HrmService.queryData` calls `executeDynamicQuery`; `buildDynamicQuery` validates names and values against the registry and inserts trusted company scope; PostgreSQL executes the parameterized SELECT in a read-only transaction; the result is converted to JSON `{dataset, rows, count, limit, offset}` and returned through MCP for Agent explanation. `companyId` or `employeeId` in the query body is rejected as an unknown key. No existing repository method is replaced.

Files added: `hrm-server/src/dynamicQuery.js` (registry, validator, builder, executor), `hrm-server/tests/dynamicQuery.test.js`, `hrm-server/tests/dynamicQuery.postgres.test.js`, and this plan. Business services and schema are unchanged.

Read-only catalog queries through the existing admin credential confirmed that neither `hrm_identity_test` nor `hrm_test_runner` existed in that instance. The stale test URL therefore produced PostgreSQL `28P01` before the server could check whether the database existed. There was no conflicting process environment override; `DATABASE_URL` and `TEST_DATABASE_URL` were absent from the shell before loading env files. Docker networking was not the cause: both URLs target the same published local port.

`npm test` executes `node --test` without `--env-file=.env.test`. Both PostgreSQL test files set `integration = process.env.TEST_DATABASE_URL ? test : test.skip`; the variable was absent, which explains the seven original SKIPs. `npm run test:postgres` loads `.env.test` but previously reached the stale URL.

Repair: created **new** `hrm_identity_test` database and `hrm_test_runner` login role in the local PostgreSQL container, with a generated credential. Updated only ignored `hrm-server/.env.test` with the new test URL; no secret was written to tracked source and no development/production password was changed. Database `mcpserver` was not used for integration tests. Migrations 001–006 applied successfully to the new database. Read-only verification confirmed all six migration records, employee/department/attendance/leave/identity/RBAC tables, and CREATE privilege for the test owner. ## Phase 12 continuation: aggregate privacy policy proposal (2026-10-08)

Row-scope enforcement and aggregate privacy are separate controls. The DQE WHERE clause restricts every COUNT, SUM, AVG and GROUP BY to the actor's authorized company/employee/team rows; PostgreSQL-backed tests and SQL parameter traces confirm this. Within an allowed team, `GROUP BY employee_id` may produce a one-person row: `SUM(minutes_worked)=480` reveals that person's total directly, while `COUNT(*)=1` reveals participation. Grouping by `work_date` and `status` can similarly isolate one attendance record. This is the **small-group disclosure** risk, even from one query.

**Multi-query inference** can occur when every individual result looks acceptable. For example, a team total SUM of 1,800 minutes and the same SUM with one employee ID excluded of 1,320 reveals 480 minutes for that employee. COUNT with two nearby filters can reveal whether a specific employee matches a status or date; AVG plus COUNT reconstructs SUM. Suppressing only groups below a threshold does not stop this differencing. Pagination and the present per-request limits do not bound how many permitted requests an actor can make.

Proposed product decision, before implementation: specify which actor roles may receive per-employee or small-group aggregates, which fields/dimensions may be grouped or filtered, and whether direct group release requires a minimum size. If a minimum is chosen, suppress both small groups and complementary totals that would recover them; consider restricting `employee_id` grouping and highly selective filters for team readers. Decide whether query budgets, repeated-query detection, coarser date ranges or an audited export path are needed for differencing. Define how legitimate one-person teams should be handled. No threshold or filter restriction was added in this phase because the business/privacy owner has not selected a policy. **Status: analysis PASS; policy selection BLOCKED on product decision; implementation not started.**

### Aggregate privacy decision memo: candidate threshold of five employees

For evaluation, define a group as eligible only when it contains **at least five distinct employees**, not five attendance or leave rows. One employee with five records must still count as one person. Apply the rule to ungrouped team/company aggregates as well as each `GROUP BY` bucket if the policy is adopted; otherwise a one-person bucket remains visible. Example: a team of four could no longer answer “total minutes this week,” while a ten-person team could answer the overall total but might lose a daily/status breakdown whose buckets have fewer than five people. `GROUP BY employee_id` on team data would always have one person per bucket and would be suppressed. A self-only actor's own attendance/leave aggregate needs an explicit exemption or it would always disappear, despite being the actor's own data. HR actors with company-wide employee profile permission may need a separate rule because they can already read some individual profile fields, but attendance and leave permissions remain narrower.

A five-person threshold alone is insufficient. If a total has six contributors and a filtered total has five, subtracting the two reveals the sixth person's SUM or COUNT. Two overlapping groups of five can reveal a person through set difference. COUNT can reveal membership or status; SUM reveals totals; AVG with COUNT reconstructs SUM, and filtering by date/status can isolate a person's contribution. Complementary suppression, limits on selective filters/group keys, repeated-query controls and policy on previously released totals need consideration together. No threshold has been applied to DQE.

| Candidate policy | Safety | Useful questions retained | Implementation complexity |
|---|---|---|---|
| A. Keep row-level authorization; log aggregate use | Low against within-scope small-group inference | All current ad hoc questions, including one-person teams and exact breakdowns | Low |
| B. Five distinct employees per released group, with complementary suppression and restrictions on `employee_id`/selective team filters; exempt self-only reads | Better for direct small groups; differencing still needs repeated-query controls | Company/team totals and broad groups of five or more; small teams and narrow date/status breakdowns lose exact answers | Medium to high: count contributors before release, suppress related totals, define filter policy and test side channels |
| C. Preapproved coarse aggregate reports for team readers, with individual detail through existing explicitly authorized business tools | Highest predictability and auditability among these options | Standard weekly/monthly totals; fewer open-ended combinations of filters and groups | Medium: curate report set and maintain approvals, but no general-purpose inference defense |

**Recommendation for decision:** choose B only if product needs ad hoc team statistics; define the five-person rule, complementary suppression, self exemption, allowed group/filter keys, query-history controls and expected empty/suppressed response before implementation. Choose C if privacy assurance is more important than flexible team analytics. ### Actual query path and contributor cardinality

`HrmTools.QueryHrmData` serializes `HrmQueryContract` and calls `HrmApiClient.QueryDataAsync`; the client adds the internal token, authenticated Chat user ID and request ID to `POST /internal/v1/query`. `app.js` checks the token and calls `HrmService.resolveExecutionContext`, which gets the active linked employee, company, department and permissions from `AuthorizationRepository.resolveActor`. `HrmService.queryData` requires a separate `queryDb`, then `executeDynamicQuery` calls `buildDynamicQuery`. The builder owns all SQL identifiers, joins, scope predicates and bind parameters. The reader pool executes its SELECT inside `SET TRANSACTION READ ONLY` with a 3-second timeout. Neither MCP nor Chat is the authoritative place to enforce a contributor policy: they can be bypassed by another authorized internal caller, and they do not own the final SQL scope. Put any approved policy in `hrm-server/src/dynamicQuery.js`, in the same database transaction as the SELECT and **before** rows leave HRM; `scopeFor`/the validator should reject prohibited shapes, and the executor should enforce contributor/complement checks. Keep `HrmService.queryData` fail-closed when the reader pool is absent.

| Dataset and current scope | Small-group or individual disclosure surface | Records versus distinct employees |
|---|---|---|
| `employees`: company, only `employee.profile.read.any` | `COUNT(*)` and `COUNT(field)` with filters such as `employment_status`, `department_id/name`, `title`, exact `id`, name `contains`, or `email`; `GROUP BY` department/status/title/id/name. A one-person group or a filtered count of 0/1 reveals membership or an attribute. Email is select/filter only, not a group/aggregate field. Existing authorized list access already returns individual profile fields, so an aggregate-only threshold would not create a complete privacy boundary. | Employee ID is unique; one selected employee row represents one employee. `COUNT(field)` excludes NULLs, unlike `COUNT(*)`. |
| `attendance_records`: company plus linked department for `attendance.read.team`, otherwise own employee for `attendance.read.self` | Team `GROUP BY employee_id`, `work_date`, `status`, or combinations can make one-person cells; exact `employee_id`, one-day date range, status and minutes filters can isolate a person. `COUNT(*)`/`COUNT(id)` count days, `COUNT(minutes_worked)` counts non-NULL minute values, and `SUM`/`AVG`/`MIN`/`MAX(minutes_worked)` reveal or bound a person's time. The recorded one-day `status=present` group of 1 is direct evidence. | Unique `(company_id, employee_id, work_date)` prevents duplicate employee-days, but a 5-day aggregate can still contain only one employee. Use `COUNT(DISTINCT a.employee_id)` for a contributor test, not record count. For a numeric release, decide whether the five contributors must each have a non-NULL `minutes_worked`; otherwise one numeric contributor can determine SUM/AVG despite five employee rows. |
| `leave_requests`: company plus own employee and `leave.read.self` | `COUNT`, `SUM/AVG/MIN/MAX(requested_days)`, status/type/date grouping and filters can return one request. Current SQL never aggregates other employees' leave for this dataset; it is an intentional self-only read. | Many leave requests can belong to the same employee. A five-employee rule cannot pass without an explicit self exemption. |

The response's `count` is `rows.length` after `LIMIT/OFFSET`: for grouped queries it is the number of returned buckets, **not** the number of employees or records. Grouped `COUNT(*)` counts rows; `COUNT(field)` skips NULL; neither is a distinct-person check. `SUM`/`AVG` ignore NULL numeric values, and `AVG` plus a count can reconstruct a sum. Because arbitrary allowed filters can overlap, two individually eligible queries can differ by one employee: a six-person total minus a five-person filtered total reveals that person's value. Suppressing a small group alone also fails when an all-company/team total and the other visible groups reveal its complement. Pagination, alternate grouping, NULL groups, and repeated date/status predicates add more ways to form overlapping cohorts. The limits on filters, date span and query rate do not establish a privacy guarantee. Row scope prevents cross-company or unauthorized-row access; it does not by itself prevent inference about a person inside the authorized scope.

### Policy options for product/privacy approval

| Option | Benefit | Cost and remaining inference |
|---|---|---|
| 1. Reject the entire aggregate query when any result has fewer than five distinct employees | Simple response contract; no small bucket is returned by that request. Check the unpaginated result and each bucket, including NULL groups, before `LIMIT/OFFSET`. | A rejected query itself reveals that a cohort is small. A six-person total and a five-person filtered total can still be subtracted; grouped totals and other endpoints can reveal complements. Legitimate small teams lose statistics. |
| 2. Hide only groups with fewer than five distinct employees | Retains large groups and is useful for broad breakdowns. | The returned total, other groups, pagination or a second query can recover a hidden group. Hiding the group's label/row does not solve complementary disclosure; implementing safe secondary suppression becomes complex. |
| 3. Rule by dataset, scope and data type | Can exempt self-only leave/attendance, account for company-wide profile access, and treat team minutes more strictly than employee headcounts. It can reject risky query shapes in the trusted builder before SQL. | Requires a documented allowlist and tests for filters, grouping, NULL numeric values, complementary totals and repeated queries. A five-person check still needs limits on overlapping queries; direct list readers and legacy tools remain part of the privacy boundary. |

**Recommended MVP decision, not implemented:** choose option 3 with whole-query denial for disallowed shapes; do not silently omit buckets. Keep self-only attendance and leave aggregates as an explicit exemption. Do not release team `employee_id` groups or exact-employee filters. Because arbitrary overlapping filters can defeat a threshold, restrict multi-person aggregate filters/group keys to a small, fixed set of non-overlapping shapes approved by the owner; until those shapes are defined, withhold team numerical/grouped aggregates rather than claim the threshold is protective.
